# Down Check

**English** · [简体中文](README.zh-CN.md)

**Live:** https://down.1ms.dog

Which services are down right now? Down Check watches 210 services people search for during an outage — ChatGPT,
GitHub, Discord, Cloudflare, Netflix, Steam and the rest — from two places: our own probes in Tokyo and Shanghai, every
10 minutes. Each page shows the current state first, the last 24 hours as a strip, and the interruptions of the last
7 days.

- **Current state first.** A large online / partial / offline / unconfirmed state, then the history. Every service
  shows its own icon, so a page of names is recognizable at a glance.
- **Only our probes decide.** A service is never called "down" because one probe failed: a 403, a 429 or a challenge
  page is **unconfirmed**, and data older than 20 minutes (two missed rounds) is **cannot judge**. The service's own
  status page is linked at the bottom of its page, for reference only — it is not part of the verdict.
- **Share the live page.** Every page has a Share button next to its state or summary; it opens the shared dialog the
  other 1ms.dog tools use, draws a card of the state at share time, and links the live page. The card's date is the
  measurement date, so a reader knows how old the snapshot is.
- **10 languages**: English, 简体中文, 繁體中文, 日本語, 한국어, Español, Français, Deutsch, Português, Русский.
- **All services, all languages**: `/`, `/<group>/` and `/<group>/<service>/`.

## How a verdict is made

| State | What it means |
|---|---|
| Online | Our probe in Tokyo and/or Shanghai answered. |
| Recovered | Answering now; there was an interruption in the last 24 hours. |
| Partial | One place answers and the other does not. |
| Unconfirmed | Every answer was a refusal (403/429) or a challenge page: no way to say either way. |
| Offline | No place answers now, for less than a day. |
| Offline for days | No place has answered for more than a day: more likely our check than the service. |
| Data is stale / No data | Every source is older than 20 minutes, or there is no data. Grey, never red. |

## Run it locally

```bash
npm ci
npm run build                        # src/ + static/ → public/ (not committed: 2,320 pages)
npm run dev                          # build, then http://localhost:8791/
npm test                             # build, then the model, strings, data and page tests
```

To see live probe data, build and run the probe first (Go 1.22+):

```bash
cd probe && go build -o ../../down-probe . && cd ..
./down-probe --out probe/out --services probe/services.json --from "Tokyo, JP"
npm run dev
```

`npm run dev` reads `probe/out/latest.json` (Tokyo) and `probe/out/sh/latest.json` (Shanghai, optional). With no probe
file the rows say "no data" — the correct degraded state, not an error. For local design work, `scripts/dev.mjs` fills
the part of the 24-hour strip the probe does not have yet from the existing hourly summary; set `DOWN_BASELINE_URL`
to that JSON (the address is not in this repository). Production does not do that.

## Deploy

The Worker serves static assets and one endpoint (`/api/status.json`) that merges the two probe files, trims them to
what a page shows, caches 60 s, and keeps the last good copy for a week (marked `stale`). No cron and no KV: the
verdict uses only what the two probe machines wrote.

- `public/` is not committed: Workers Builds runs `npm ci && npm test` and then `npx wrangler deploy`; the test builds
  the site first.
- No custom domain: on 1ms.dog the shell routes the hostname to this Worker.
- The upstream addresses are not in this repository: set `PROBE_TOKYO_URL` and `PROBE_SHANGHAI_URL` in the deployment
  (Cloudflare Worker variables) to the published probe files. Without them the page says it cannot read the data.

## Data

`probe/latest.json` (one per machine): `at`, `every`, `from`, `complete`, and per service `ok`, `unknown`, `ms`,
`http`, `err`, `t` (this service's own measurement time), `h` (history, 10-minute samples), `up24`, `up7`, `out`.
The Worker trims it to the published services and the last 144 samples (`h24`) before any browser sees it. Nothing
about visitors is collected: the page reads one same-origin JSON and sets no cookies.

## Layout

```
src/services.mjs        the 210 services and 21 groups (generated from data/)
src/model.mjs           verdict, freshness and error mapping (shared by the page and the tests)
src/status-sources.mjs  the services' own status pages (links only)
src/data.mjs            what the Worker keeps from a probe file
src/worker.js           /api/status.json
src/app.js              fills the page from the JSON
scripts/gen-services.mjs  data/baseline.json + data/unlock.json → src/services.mjs + probe/services.json
scripts/build.mjs       2,320 static pages, sitemap, robots, llms.txt, _headers
scripts/icons.mjs       one favicon per service, fetched at build time into static/icons/
static/assets/share/     the shared dialog, copied verbatim from the shell (never edit here)
scripts/assets.mjs      link-preview images, one per language
probe/                  the 10-minute probe (Go), its systemd units and measured cost
```

The service icons are fetched once, at build time, and committed as `static/icons/<id>.png`; the pages serve them from
this origin, so no third-party request is made for a visitor. A service without an icon falls back to a short monogram.

The share dialog is the shell's `assets/share/` copied verbatim into `static/assets/share/`; `_headers` serves it with
`max-age=0, must-revalidate`. The pages import it only when someone clicks Share (`?v=10`). The link is the live page,
not a frozen result; the card shows the state and the measurement date at share time. `sites.js` can use
`/zh-cn/ai/chatgpt/` as the sample share link.
