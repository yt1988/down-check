# down-probe

Measures every service in `services.json` from one machine, one request each, every 10 minutes, and writes
`latest.json`. Run it once per place: Tokyo and Shanghai each write their own file and the page shows them separately.
It is the measurement side of down.1ms.dog; the page and the Worker are in the parent folder.

## What it does

- Reads `services.json`: `[{ "id": "...", "url": "https://...", "alt": ["https://..."] }]` (generated by
  `scripts/gen-services.mjs` from the registry; 210 targets, all unique). `alt` is optional.
- Spreads the round over 45 seconds (default), with at most 20 requests in flight, so 210 services do not hit at one
  second. One request per service, 8 s timeout, `Range: bytes=0-0`, at most 4 KB of body read. It sends a normal
  browser User-Agent and Accept headers: a 403 for a named bot says nothing about whether people can reach the service.
  A few front pages are too heavy (or answer on another host), so those unlock services are probed by their favicon.
- A blocked favicon or front page is not the service. When the usual URL is not a definite answer (403, 429, a 5xx,
  a timeout), the probe tries the fallbacks in `alt`: normally the same host's `robots.txt` and front page, and for a
  few services an API host (Mistral, Telegram) or the one path that is not challenged (Bahamut). The service is up if
  any of its own addresses answers. The fallbacks are only requested after the usual URL fails, so a normal round still
  makes one request per service.
- **200–399 and 4xx (except 403/429): answered.** **403, 429, a 5xx, `cf-mitigated: challenge`, "Just a moment" /
  "Attention Required": unconfirmed** — the service answered, but it is blocking us or erroring; one probe cannot tell
  whether that is the service or our IP. **Timeouts, DNS/TLS/reset errors: no answer.**
- Writes a run into `days/YYYY-MM-DD.json`, then rebuilds `latest.json` from the last 7 days (so a wrong history fixes
  itself on the next run). Keeps 30 days of day files.
- Per service: the latest result, **its own measurement time `t`** (a round is not one instant), `h` (history, oldest
  first: `o` answered, `u` unconfirmed, `x` no answer, `-` not measured), `up24`, `up7`, and the runs with no answer.
- A service that was not measured in a round keeps its last real sample and an older `t`; it is never written as a
  failure. A round that does not finish in time is written with `complete: false` and the missing services as `-`.
- Atomic writes; only its own folder; no logs about visitors (there are none).

## Measured (2026-11-25, macOS, 210 services)

| | |
|---|---|
| Round time | **45.6 s** from Tokyo with the default 45 s spread; **92.6 s** from Shanghai (many timeouts) |
| Peak RSS | **40 MB** (`/usr/bin/time -l`) |
| Response bodies read | **about 262 KB** per round from Tokyo; fallbacks are read only when the usual URL fails |
| Requests | 210 per round normally, up to about 630 if every service needs its fallbacks (rare) |
| Network | about 9 GB/month including TCP/TLS overhead, per machine |
| Outcome of the test round | Tokyo: 204 answered, 6 unconfirmed (403/challenge/5xx), 0 no answer. Shanghai: 137 answered, 20 unconfirmed, 53 no answer. Together, any place answering: **204 online, 6 unconfirmed, 0 offline**. |

Use `MemoryMax=128M` (about 3.5× the measured peak), `TimeoutStartSec=540`, and a 10-minute timer. The output with
7 days of history is about 300 KB; the Worker trims it before sending anything to a browser.

## Run

```bash
go build -o down-probe .
./down-probe --out /tmp/down --services services.json --from "Tokyo, JP"
go test ./...
```

Flags: `--out` (required), `--from` (label shown on the page), `--services`, `--concurrency` (20), `--timeout` (8s),
`--spread` (45s), `--every` (600, written to the file), `--max` (8m, whole round).

## Install (the deployment on 1ms.dog; the systemd files here are the shape)

1. `/opt/1ms/down/down-probe` (root:root 755) and `/opt/1ms/down/services.json` (644).
2. A user `1ms-down` with no login shell and the result folder writable by it:
   `/srv/1ms-data/down` (owner `1ms-down`).
3. Copy `1ms-down-probe.service` and `1ms-down-probe.timer` to `/etc/systemd/system/`, then
   `systemctl daemon-reload && systemctl enable --now 1ms-down-probe.timer`.
4. The result folder is published read-only by the data host at `/down/latest.json` (the
   Worker's `PROBE_TOKYO_URL` points at the published `down/latest.json` on your data host).
5. Shanghai: the same binary and `services.json`, `--from "Shanghai, CN"`, its own output folder, and a URL the Worker
   can read (`PROBE_SHANGHAI_URL`). The Worker merges the two; neither overwrites the other.

Verify: `systemctl start 1ms-down-probe`, then
`curl -s https://<your-data-host>/down/latest.json | head -c 200` — `at` is recent, `count` is 210, `complete` true.
